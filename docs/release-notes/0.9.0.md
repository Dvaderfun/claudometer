# Claudometer 0.9.0 — proposed trust-root release

**Draft for the human release owner. Not a published release.** The recommended
version is 0.9.0; `Cargo.toml` remains 0.7.3 until the owner chooses and bumps it.
Replace all pending verification values below before publication.

## Manual installation required

All published versions through 0.7.3 lack an embedded Ed25519 release key and
cannot authenticate this first trust-root release. Install it manually after
independent verification. The old updater must not install across this boundary;
the bootstrap release must omit the legacy `claudometer.exe` and
`claudometer.exe.sha256` asset aliases.

Choose the matching Windows 11 asset:

- x64: `claudometer-v0.9.0-windows-x64.exe`
- ARM64: `claudometer-v0.9.0-windows-arm64.exe`

Obtain the expected values from these release notes **and** the separately
authenticated record listed below. Both records must agree. A checksum fetched
beside the executable alone is not independent verification.

| Required published value | Owner must supply |
|---|---|
| Exact version/tag | Pending owner choice; proposed `0.9.0` / `v0.9.0` |
| x64 executable SHA-256 | Pending final signed artifact |
| ARM64 executable SHA-256 | Pending final signed artifact |
| Authenticode publisher subject | Pending validated publisher |
| Authenticode certificate SHA-256 fingerprint | Pending signing certificate |
| Ed25519 release public key and raw-key SHA-256 fingerprint | Pending production key |
| Initial embedded release sequence | Pending positive production sequence |
| Provisioned at (UTC) | Pending |
| Separately authenticated verification record | Pending owner-controlled location |

Do not run a download with placeholder values, mismatching records, or an
invalid/missing signature. From PowerShell, replace the expected values with
those obtained from both published records:

```powershell
$asset = Resolve-Path '.\claudometer-v0.9.0-windows-x64.exe'
$expectedSha256 = '<64 lowercase hex characters from both records>'
$expectedPublisher = '<exact Authenticode subject from both records>'
$expectedCertSha256 = '<64 lowercase hex characters from both records>'

$actualSha256 = (Get-FileHash -LiteralPath $asset -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actualSha256 -cne $expectedSha256) { throw 'Claudometer SHA-256 mismatch' }
$signature = Get-AuthenticodeSignature -LiteralPath $asset
if ($signature.Status -ne 'Valid') { throw "Invalid Authenticode signature: $($signature.Status)" }
if ($signature.SignerCertificate.Subject -cne $expectedPublisher) { throw 'Unexpected publisher' }
$hasher = [Security.Cryptography.SHA256]::Create()
try {
    $actualCertSha256 = ([BitConverter]::ToString(
        $hasher.ComputeHash($signature.SignerCertificate.RawData)
    )).Replace('-', '').ToLowerInvariant()
} finally {
    $hasher.Dispose()
}
if ($actualCertSha256 -cne $expectedCertSha256) { throw 'Unexpected signing certificate' }
```

Use the `arm64` filename on ARM64. After all checks pass, quit the existing
Claudometer normally, confirm any lid recovery is complete, and replace the
portable executable. Retain settings and recovery files. Launch the verified
copy; Claude Code and Codex continue to own sign-in and credentials. Further
releases can use authenticated updates once this trust root is installed.

Full contract: [trust-root bootstrap](../release-manifest-v1.md#trust-root-bootstrap).

## What changes for users

- Settings writes use validated atomic commits, retain a verified backup, and
  preserve malformed files for recovery. Existing preference fields and unknown
  keys survive migration.
- Account/request isolation rejects obsolete provider results. A failed fetch
  cannot silently attach the previous account's plan or usage to a new account.
- Alerts use newly accepted successful fetches and account/limit/reset identity;
  stale data does not trigger a new alert. Official CLIs remain the sole
  credential writers, and polling never refreshes provider tokens.
- Vibecode's tray/flyout switch holds only a wake lock. The independent Advanced
  lid setting journals and verifies persistent power changes, restores the
  recorded scheme conservatively, and retains actionable recovery state after
  an interruption.
- Portable updates authenticate a signed manifest, architecture, version,
  sequence, expiry, exact size, and SHA-256 before writing a candidate. A durable
  update journal and nonce/PID/hash-bound readiness handshake retain the previous
  verified executable until commit. Managed or ambiguous installs use the
  explicit release-page action.
- **New installations default automatic update checks off.** Enable them in
  Settings to check GitHub at startup and at most daily. Existing settings
  documents migrate to enabled; the same toggle can disable future checks.
- The flyout and Settings expose named UI Automation controls and keyboard
  focus. Narrator verification is deferred, and Selection/RangeValue patterns
  and targeted property events remain incomplete; this release makes no
  screen-reader-support claim.
- The size profile reduces measured local provisioned builds to 1,058,304 bytes
  x64 and 940,544 bytes ARM64 before Authenticode signing. Final signed sizes
  and hashes must be measured again. Windows native rendering and the single
  process architecture are preserved.

The bounded parsers, local fixture/state tests, daily update consent, and
documented [privacy contract](../../PRIVACY.md) add no telemetry or crash upload.

## Legacy Vibecode recovery notice

Older `settings.json.vibecode_lid` values have no recorded scheme GUID. They
block a new lid override until the user explicitly chooses **Restore** in
Settings, which applies the saved AC/DC pair to the current scheme after
journaling and read-back verification. Claudometer does not guess the old scheme.

If needed, after quitting normally, run the verified executable with
`--recover-vibecode`. This is an explicit request to recover recorded power
state; for legacy values it applies them to the current scheme. A nonzero result
means recovery remains unresolved: stop installation/removal and retain the
journal, backups, corrupt siblings, and settings for inspection. Never delete
or hand-edit a recovery journal to bypass the error.

See [Vibecode recovery](../recovery/vibecode.md).

## Human publishing checklist — do not tag until complete

1. Choose the production publisher and provision/wire Authenticode signing.
   **Current `release.yml` signs Ed25519 manifests but has no Authenticode
   signing/verification step.** The bootstrap contract requires valid signed
   executables; merely provisioning the manifest key is insufficient. Integrate
   signing before final hashing/manifests/attestations and preserve immutable
   artifact checks. Do not trigger the automatic publishing workflow yet.
2. Generate and securely retain the offline Ed25519 key. Provision
   `CLAUDOMETER_RELEASE_PRIVATE_KEY_PKCS8_B64` and
   `CLAUDOMETER_RELEASE_ADMIN_READ_TOKEN` in the protected `release` environment;
   configure `CLAUDOMETER_RELEASE_PUBLIC_KEY_HEX`, a positive monotonic
   `CLAUDOMETER_RELEASE_SEQUENCE`, and `CLAUDOMETER_MINIMUM_UPDATER_VERSION`.
   The public key/sequence must match the executable policy and signed evidence.
3. Record the production publisher, certificate/key fingerprints, sequence,
   independent record URL, and UTC provisioning entry in
   [the production bootstrap record](../release-manifest-v1.md#production-bootstrap-record).
   Complete real Windows 11 ARM64 runtime validation; local cross-compilation
   does not prove runtime safety. Confirm the documented Narrator deferral.
4. Choose the version, bump `Cargo.toml`, promote the Unreleased notes to the
   chosen version, and submit the change through a PR with all five required
   checks. Validate both final signed artifacts against the 1.25 MiB ceiling.
5. Run `ci/check-release.ps1` for the chosen tag/assets, including
   `-RequireEvidence` with the real public policy. Run
   `ci/check-release-infrastructure.ps1` with the protected release environment
   credential. Verify signatures, manifests, SBOM, and downloaded attestations.
6. The human pushes the immutable tag and approves the `release` environment.
   The workflow then smoke-tests and publishes automatically. After success,
   the human applies these completed notes with `gh release edit <tag>
   --notes-file docs/release-notes/<version>.md`. Never reuse a version/tag.
